# `exceptions.c` / `exceptions.h` — CPU Exception Handler

Catches CPU exceptions (#DE through #PF, plus the ones the
kernel bothers with), paints a blue screen with the exception
name, and halts the CPU. The handler is registered in the IDT
during `kernel_main`.

## Public API (`exceptions.h`)

```c
void exceptions_install(void);
```

That's the entire public surface. `exception_handler_c` is
called from the assembly stubs in `main.asm` and is not
intended to be called directly.

## Assembly stubs

The C side registers stubs for vectors `0, 1, 2, 3, 4, 5, 6,
7, 8, 13, 14`. Those vectors are generated by macros in
`main.asm`:

```asm
%macro EXCEPTION_NOERR 1
global exception_stub_%1
exception_stub_%1:
    push dword %1
    call exception_common
%endmacro

%macro EXCEPTION_ERR 1
global exception_stub_%1
exception_stub_%1:
    push dword %1
    call exception_common
%endmacro
```

Both macros push the vector number and call `exception_common`,
which pushes all registers, calls `exception_handler_c(vector)`,
and never returns (because the C handler halts). See
`kernel-entry.md` for the full stub layout.

The distinction between the two macros is for future use:
`EXCEPTION_ERR` is for vectors that the CPU itself pushes an
error code for (8, 10, 11, 12, 13, 14, 17, 30). Today the
macros do the same thing — push the vector number — but the
intent is that the ERR macro would not need to push a
placeholder error code.

## `exceptions_install`

```c
void exceptions_install(void) {
    set_idt_gate(0,  (unsigned int)exception_stub_0);
    set_idt_gate(1,  (unsigned int)exception_stub_1);
    set_idt_gate(2,  (unsigned int)exception_stub_2);
    set_idt_gate(3,  (unsigned int)exception_stub_3);
    set_idt_gate(4,  (unsigned int)exception_stub_4);
    set_idt_gate(5,  (unsigned int)exception_stub_5);
    set_idt_gate(6,  (unsigned int)exception_stub_6);
    set_idt_gate(7,  (unsigned int)exception_stub_7);
    set_idt_gate(8,  (unsigned int)exception_stub_8);
    set_idt_gate(13, (unsigned int)exception_stub_13);
    set_idt_gate(14, (unsigned int)exception_stub_14);
}
```

Eleven gates, one per installed vector. The numbers must
match the macro invocations in `main.asm`; the C side is the
"installer" and the assembly side is the "stubs".

## `exception_handler_c`

```c
const char* exception_names[] = {
    "Divide by Zero", "Debug", "Non-Maskable Interrupt", "Breakpoint",
    "Overflow", "Bound Range Exceeded", "Invalid Opcode", "Device Not Available",
    "Double Fault", "", "", "", "", "General Protection Fault", "Page Fault"
};

void exception_handler_c(int vector) {
    fill_screen(0x00, 0x00, 0x80);

    const char* name = (vector < 15) ? exception_names[vector] : "Unknown Exception";

    int x = 20, y = 20;
    for (int i = 0; name[i]; i++) {
        draw_char(x, y, name[i], 0xFF, 0xFF, 0xFF, 2);
        x += 18;
    }

    __asm__ volatile ("cli");
    for (;;) { __asm__ volatile ("hlt"); }
}
```

On entry, the handler:

1. Paints the entire screen blue (`0x00, 0x00, 0x80` =
   B=0, G=0, R=0x80, which displays as dark blue given the
   framebuffer's BGR byte order).
2. Looks up the exception name in `exception_names[]`. If the
   vector is `>= 15`, falls back to "Unknown Exception".
3. Draws the name at `(20, 20)` in white, scale 2 (so each
   glyph is 16×16 pixels). The `x += 18` advance is one
   scaled glyph width plus a small gap.
4. Disables interrupts (`cli`) and halts the CPU forever
   (`hlt` in an infinite loop).

`fill_screen` writes to the backbuffer, so the blue background
isn't visible until `screen_swap` runs. The current code never
calls `screen_swap` after the exception, so the backbuffer is
full of blue and white but the actual framebuffer still shows
whatever the last `screen_swap` left there (typically the
status bar). This is a latent bug — the blue screen "works"
only by accident if a `screen_swap` happened to occur just
before the exception. To make it actually display, the
handler should call `screen_swap` after `fill_screen`.

## `exception_names` table

The array has 15 entries (matching the index range 0..14) but
slots 9, 10, 11, 12 are empty strings. The corresponding
exceptions are reserved/unimplemented in the i386 architecture
(9 = "Coprocessor Segment Overrun", legacy; 10/11/12 = invalid
opcodes 0FA, 0FB, 0FC, 0FD), so the empty strings are
defensive. If one of them ever fires, the blue screen will
display an empty line.

Indices and names:

| Index | Exception |
|---|---|
| 0 | Divide by Zero |
| 1 | Debug |
| 2 | Non-Maskable Interrupt |
| 3 | Breakpoint |
| 4 | Overflow |
| 5 | Bound Range Exceeded |
| 6 | Invalid Opcode |
| 7 | Device Not Available |
| 8 | Double Fault |
| 9..12 | (reserved) |
| 13 | General Protection Fault |
| 14 | Page Fault |

## Caveats

- **No `screen_swap` after `fill_screen`.** The blue screen
  is computed into the backbuffer but never pushed to the
  framebuffer. Either add a `screen_swap()` call or do the
  fill directly into `screen.framebuffer` if a true panic
  screen is desired.
- **No register dump.** A useful exception handler would
  print at least EIP, CS, EFLAGS, and the error code (for
  #DF, #GP, #PF). This one only prints the name.
- **No error code access.** The CPU pushes an error code for
  #DF, #GP, and #PF. The stubs in `main.asm` could pass it
  through to `exception_handler_c`, but they don't.
- **No stack trace.** With paging off, the kernel stack is at
  a known linear address; walking EBP frames would be
  straightforward. Not implemented.
- **No way to recover.** Once an exception fires the kernel
  halts. There's no task to return to.
